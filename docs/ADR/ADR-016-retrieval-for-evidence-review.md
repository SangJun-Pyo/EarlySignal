# ADR-016: 분류 검증을 먼저 하고 RAG는 근거 검색 확장으로 설계한다

- 상태: 채택 (확장 설계만 승인, 구현 미완료)
- 날짜: 2026-10-09
- 관련: ADR-004, ADR-009, ADR-012, ADR-013, ADR-015

## 배경

현재 분류는 식별정보를 정제한 신고 한 건을 LLM에 직접 입력해 Structured Outputs로 고정 항목을 받는다. 임베딩·pgvector·벡터 검색은 사용하지 않는다. 출력 스키마, 원문 인용 일치, 길이, 식별정보 검사는 자동으로 수행하지만 의미상 라벨의 정답을 보증하지 않는다. 고정 50건 시험과 사람 정답 검수는 아직 완료되지 않았다.

사용자는 현재 방식을 확인한 뒤 **분류 검증 우선 + RAG 근거 검색 확장 설계**를 선택했다. 실제 API·DB 추가 구현은 이 결정의 범위가 아니다.

## 결정

1. 먼저 같은 신고에 대한 키워드·직접 LLM 분류를 사람이 확인한 정답과 비교한다. 검수 예시를 분류 지침에 반영할 때는 개발용 검수 자료와 최종 평가 표본을 분리하고 프롬프트 버전을 기록한다. 방법 간 일치율과 사람 정답 기반 정확도를 구분한다.
2. 검색 증강 생성(RAG)은 유사 과거 신고와 권한이 있는 수리·생산 자료를 찾는 **담당자 근거 검토 보조**로 설계한다. 현재 신고의 자동 라벨에는 다른 신고의 사실을 섞지 않는다. 검색이 통계 경보 규칙이나 원래 집계를 바꾸지 않는다.
3. 확장 흐름은 `정제된 자료 → 임베딩 → PostgreSQL + pgvector → 기준일·권한 필터가 적용된 유사 근거 검색 → 출처 ID를 연결한 RAG 요약 → 담당자 원문 대조`다. 이 전체 흐름은 현재 미구현이다.
4. 접수일과 자료 이용 가능일을 구분해 보관한다. 해당 분석 기준일 이후 자료, 조사 결과·사후 정답, 접근 권한 밖 자료가 검색 결과나 요약 입력에 섞이지 않도록 한다. 회고 검증에서 당시 공개 상태를 재구성하지 못하면 그 한계를 유지한다.
5. 반환된 검색 결과의 원문 ID·자료 버전·기준일·권한 범위·인용 위치를 보존한다. 입력과 검색 결과는 비신뢰 데이터로 취급하고, 요약은 검색된 근거 안에서만 작성한다. 출처 밖 인용은 폐기하고 의미적 일치는 사람이 검토한다.
6. 검색 검증은 사람이 표시한 관련 문서 기준 `Recall@k`, 기준일·권한 누출 여부, 인용의 원문 일치와 의미 정확성, 담당자 검토 시간을 따로 측정한다. 현재 어느 지표도 측정하지 않았다. 도입 여부는 직접 분류와 근거 검토의 실측 개선을 본 뒤 결정한다.

## 절충과 범위

검색으로 더 많은 근거를 보여줄 수 있지만 유사 표현이 같은 고장이나 원인을 뜻하지는 않는다. 검색 누락·중복·시점 누출·접근 권한 오류와 추가 비용이 생긴다. 신고 원문과 기존 근거 검토 기능을 유지하고, 실제 DB·임베딩 모델·자료 연결·비용 승인은 별도로 정한다. 현재 정적 웹에는 벡터 저장소나 서버를 추가하지 않는다.

## 검증 계획

- 분류: 사람이 확정한 동일 표본의 키워드·직접 LLM 라벨을 비교하며 잘못 묶은 사례와 누락 사례를 함께 기록한다.
- 검색: 기준일 이전·이후와 권한 허용·금지 문서를 섞은 평가 자료로 누출 차단을 검사한다.
- 근거: 관련 문서 정답 목록 대비 Recall@k, 원문 ID·인용 일치, 의미 왜곡을 각각 평가한다.
- 업무: 동일 과제에서 원문 검토 시간과 요청서 근거의 타당성을 비교한다. 효과 수치는 실행 전까지 비워 둔다.
