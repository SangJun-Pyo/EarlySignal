# ADR-022: 문제를 이슈·작업 브랜치·PR·독립 검수로 연결한다

- 상태: 채택
- 날짜: 2026-10-09
- 관련: ADR-010, WORKFLOW

## 사용자 제안과 결정
사용자가 문제가 생기면 GitHub 이슈로 등록하고, 서브에이전트가 하위 브랜치에서 작업한 뒤 PR로 검토·통합하는 방식을 제안했다. 총괄은 이를 채택했다.

## 절차
1. 문제를 실제로 확인한 뒤 중복 이슈를 찾고, 재현 조건·영향·수정 범위·완료 조건을 이슈에 적는다. 민감정보와 원문 전체는 공개 이슈에 붙이지 않는다.
2. 구현 에이전트에게 이슈 URL, 소유 파일·검증 범위·기준 브랜치를 전달한다. 기능 브랜치는 `codex/` 접두사를 사용한다.
3. 병렬 구현은 별도 managed worktree로 분리한다. 기존 파일이나 다른 에이전트의 변경을 덮어쓰지 않는다. 같은 코드의 읽기 검수는 공유 경로에서도 가능하다.
4. Step 단위 커밋과 세션 로그를 유지한다. PR에는 문제와 최종 동작, 실제 검증, 남은 한계를 적고 관련 이슈를 연결한다.
5. 구현자와 다른 에이전트가 검수한다. 총괄은 지적 반영·필요 테스트·통합 범위를 확인하고 통합한다. CI와 수동 원문·실제 배포 검수는 서로 대체하지 않는다.
6. 기존 커밋을 rebase/squash로 지우지 않고 merge commit으로 PR과 작업 이력을 보존한다. 충돌은 해당 변경의 목적과 증거를 대조해 해결한다.

## 전환 시점
전체 LLM 실행 중 전환했다. 이전부터 구현·검수하던 작업은 이슈 #1과 `codex/llm-evidence-validation`으로 추적하고, 이슈 이전 작업이었다는 사실을 기록한다. 새 CI 작업은 이슈 #2를 먼저 만든 뒤 별도 worktree와 브랜치를 할당했다. 과거 개발이 모두 이슈 기반이었다고 소급하지 않는다.

## 절충
이슈·PR에 따른 작은 관리 비용이 추가되지만 변경 목적, 검수자, 실패와 수정의 연결이 명확해진다. 같은 문제의 작은 수정은 같은 이슈·PR에 모으고 모든 문구 변경마다 별도 이슈를 만드는 식으로 작업을 늘리지 않는다.

## 변경 이력
- 2026-10-09, 이슈 #8 / S24: 하위 기능 브랜치를 대상으로 한 PR도 같은 CI 검사를 받도록 `pull_request`의 대상 브랜치 제한을 제거한다. `main` push 검사·최소 읽기 권한·기존 테스트 작업을 유지하며 `pull_request_target`으로 바꾸지 않는다. 실제 하위 PR의 Python·웹 CI 성공으로 확인한다.
