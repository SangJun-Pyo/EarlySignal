# R02 — 요청서·시점 차단·API 중단 독립 검수

- 날짜: 2026-10-09 (Asia/Seoul)
- 역할: 제품 구현 담당과 분리된 검수 에이전트
- 범위: `web/lib/request.ts`, `web/lib/asof.ts`, 웹 통합 코드, export/brief, LLM 호출 중단
- 상태: 현재 키워드 제품의 요청서·시점 함수 및 정적 통합 검수 완료. 브라우저 시나리오 검수는 부모 에이전트가 별도로 수행한다. LLM 브리프는 비활성 상태로 두고 아래 보완 항목을 유지한다.

## 검수로 발견하고 수정한 사항

### R02-01 / P1 — 증상이 다른 요청서의 문서번호 충돌

초기 문서번호는 category의 첫 단어만 사용했다. 같은 차종·월의 `engine_stall`과 `engine_failure`가 모두 `ENGINE`이 되어 결정 기록이 충돌할 수 있었다. 제조사·모델·전체 증상 코드를 사용하도록 구현과 계약을 수정했다. 두 증상을 연속 선택하여 서로 다른 문서번호가 나오는 테스트를 추가했다.

### R02-02 / P1 — 손상된 근거의 날짜·건수 불변식

초기 요청서와 시점 함수는 접수일 상한만 검사하여 이전 달 접수 신고가 잘못된 month 필드와 함께 들어오면 통과했다. `month <= ldate < 다음 달 1일`로 검사하도록 보완했다. 중복 evidence ID, `evidence.n != unique ids 수`, `alert.n != evidence.n`, 부적절한 기준선도 요청서 생성 시 거부한다.

### R02-03 / P1 — 짧은 잘못된 인용 번호가 검사를 우회

초기 웹 인용 정규식은 5자리 이상만 찾았다. 유효한 번호 옆의 `#12`는 검사되지 않고 AI 브리프에 남을 수 있었다. 모든 `#숫자` 참조를 근거 집합과 비교하도록 수정했다.

### R02-04 / P1 — 제외한 근거의 AI 재인용 차단

담당자가 제외한 번호가 기존 AI 브리프에 있으면 브리프 전체를 요청서에서 빼고 이유를 표시한다. 근거 밖의 번호 또는 번호 없는 브리프도 사용하지 않는다. 통계·상황 집계는 최초 분류 모집단 기준이며 담당자의 제외는 인용 선택에 반영된다는 설명을 유지한다.

## 통합 수정 확인

1. 웹 원문 목록이 `getAsOf` 결과를 사용하며 근거 목록도 차종·증상·월·접수일 하한/상한을 검사하도록 수정한 것을 확인했다.
2. 동일 신호를 다시 저장할 때 이전 결정을 보존하도록 append 방식으로 수정했다. 표시 key도 문서번호와 저장 시각을 함께 사용한다.
3. 연기·주행·주차 표현은 키워드 규칙, 심각도는 미측정으로 문구를 구분한 것을 확인했다.
4. 공개 발췌의 known-value 정제를 export에서 호출한 것을 확인했다. `test_contract.py`, `test_request.py`, `test_label_quota.py` 대상 독립 실행: **18 passed**. 출력 스키마·체크섬·참조·집계·개인정보 패턴·미래 값 분리를 검사한다. 향후 LLM 문장의 의미 정확성까지 보증하는 테스트는 아니다.

현재 활성화된 키워드 요청서 흐름의 통합에 이견 없음. 실제 저장·다운로드·화면 상호작용은 브라우저 검수 결과를 별도로 확인한다.

## AI 브리프 검증의 추가 한계

### R02-05 / P1 / 현재 제품은 briefs={} — 숫자의 값 일치만으로 의미를 검증할 수 없음

초기 `validate_brief`는 여러 집계의 숫자를 하나의 허용 집합으로 합쳤다. `injury=0`, `fire=1`인 합성 근거에서 “부상 1명”과 “사망 1명”이 모두 통과하는 것을 독립 실행으로 확인했다. 숫자 1이 다른 집계에 존재한다는 사실은 부상·사망 주장의 근거가 아니다.

현재 키워드 제품의 `briefs={}`에는 해당 문장이 포함되지 않지만, 향후 LLM 브리프를 활성화하기 전에 지표와 숫자를 짝지어 검증해야 한다. 대안은 LLM의 수치 문장을 제한하고 통계 문장을 값 기반 템플릿으로 만드는 것이다. 현재 검증기를 “모든 수치의 사실성을 검증했다”고 소개해서는 안 된다. 구현 담당에게 수정·범위 명시를 요청했다.

### 데이터 출처 날짜

`meta.data_source.downloaded_at`에 실행일이 고정되어 있었다. 제공받은 ZIP의 실제 다운로드 시각을 확인하지 않았다면 생성일·검증일과 구분해야 한다. 실제 다운로드일 또는 확인 불가 상태를 기록하도록 요청했다.

원본 ZIP의 파일 크기·SHA256·압축 멤버·CRC를 담은 `data/results/source_manifest.json`이 추가된 것을 확인했다. `observed_local_date`는 로컬 확인 날짜이며 실제 다운로드 날짜를 뜻하지 않는다. 둘을 같은 필드에 연결하는 후속 구현은 이 의미를 계약에서 명시하거나 다운로드일을 미확인으로 남겨야 한다.
