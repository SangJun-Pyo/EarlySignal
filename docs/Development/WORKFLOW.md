# 작업 절차 (하네스)

이 저장소는 세 층으로 일한다.
- **1층 작업 틀**: `AGENTS.md`(지침), 이 문서(절차), `docs/SPEC.md`(단계 명세)
- **2층 기록과 근거**: `docs/ADR/`(설계 결정), `docs/Sessions/`(단계별 세션 로그), `docs/Knowledge/LessonsLearned.md`(배운 점), `docs/Contracts/`(데이터 계약) + 테스트
- **3층 기능**: `pipeline/`, `web/`

## 한 단계(Step)를 진행하는 5단계
1. **계획**: `docs/Sessions/S{번호}-{step}.md`를 양식대로 만들고 목표·완료 기준·건드릴 파일을 적는다(SPEC에서 복사).
2. **구현**: 해당 Step 범위만 구현한다. 다른 Step 파일을 건드려야 하면 세션 로그에 이유를 적는다.
3. **검증**: SPEC의 완료 기준을 실제로 실행한다. 관련 테스트(`pytest`)와 계약 테스트를 돌린다. 숫자가 현재 SPEC·공개 결과와 다르면 입력·설정·코드 버전을 대조해 원인을 기록한다. 과거 시제품 수치에 맞추기 위해 현재 규칙을 바꾸지 않는다.
4. **기록**: 세션 로그에 결과 숫자, 문제와 해결, 사람이 고친 부분을 적는다. 설계 결정이 새로 생기거나 바뀌면 ADR을 추가한다. 다음에도 쓸 교훈은 LessonsLearned에 한 줄.
5. **커밋**: `stepN: <무엇>` 한 커밋(또는 몇 개). 세션 로그도 같은 커밋에 포함. `docs/CODEX_LOG.md` 색인에 한 줄 추가.

## 이슈·브랜치·PR 연결 (2026-10-09 사용자 선택)

- 실제 문제와 기존 이슈를 확인한 뒤 재현 조건·영향·수정 범위·완료 조건을 GitHub 이슈에 적는다.
- 총괄은 구현 에이전트에게 이슈와 소유 범위를 배정한다. `codex/` 브랜치와 별도 managed worktree로 병렬 변경을 분리한다.
- Step 커밋·ADR·세션 기록을 PR에 연결한다. 다른 에이전트가 검수하고, 작성자는 지적을 수정한 뒤 재검증한다.
- 총괄이 검수·테스트·실제 동작 근거를 확인해 통합한다. PR은 merge commit으로 이력을 보존하고 이슈의 완료 조건을 함께 확인한다.
- 진행 중이던 작업을 전환할 때에는 이슈 이전 구현·검수였음을 밝힌다. 상세 결정은 [ADR-022](../ADR/ADR-022-issue-branch-pr-review.md).

## PR 자동 검증과 수동 검수

PR과 `main` push의 GitHub Actions는 전체 Python 테스트, 웹 테스트·타입 검사·정적 빌드를 실행한다. 원본 데이터·작업 DB·API 키 없이 합성 자료와 커밋된 공개 JSON을 검사한다. 검사 실패를 제외·무시하여 통과시키지 않는다.

CI 성공은 코드·계약 검사의 결과다. 원문 의미, 사람 정답 정확도, 실제 공개 배포의 브라우저 동작은 독립 검수와 수동 확인으로 기록한다. 배포는 기존 Cloudflare GitHub 연결이 담당하며 이 CI가 별도 배포하지 않는다.

## 현재 설명과 역사 기록

README·SPEC·STATUS는 현재 제품을 설명한다. ADR·세션·검수 보고는 작성 당시의 결정과 증거를 보존하며 후속 변경은 별도 기록·링크로 연결한다. 검수한 PDF·출력 해시를 보존할 때에는 해당 커밋을 명시한다. 이후 문서 변경의 해시로 덮어써 과거 검수를 재실행한 것처럼 기록하지 않는다.
